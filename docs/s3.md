Há dois caminhos para copiar os arquivos de _backup_ das _builds_ para um _bucket_ S3:

- nos servidores com **Releaser**, o comando `io cloud` (veja [Cópia em nuvem (S3)]({{ site.baseurl }}/docs/releaser#cloud));
- nos _clusters_ compartilhados, o **Backup S3** do projeto, configurado no **Dashboard** (veja [abaixo](#clusters)), que também permite **restaurar** um _backup_ do _bucket_ na _build_.

O destino pode ser um serviço comercial (AWS S3, Cloudflare R2, Backblaze B2) ou um S3 **no seu próprio _data center_**, o que mantém os dados dentro da Embrapa e não tem custo por gigabyte. O recomendado é o S3 da sua Unidade.

Esta página descreve como montar esse S3 próprio com os _boilerplates_ da plataforma, do mesmo jeito que foi montado o **Embrapa I/O S3**, e como configurá-lo nos dois caminhos. São três peças:

- **[Silo](https://silo.pigsty.io)**: servidor S3 de código aberto (um _fork_ mantido do MinIO, com o console de administração completo), pelo _boilerplate_ `silo`;
- **[Caddy](https://caddyserver.com)**: _proxy_ reverso com HTTPS automático (Let's Encrypt), pelo _boilerplate_ `caddy`;
- **[Releaser]({{ site.baseurl }}/docs/releaser)**: faz o _deploy_ dos dois e os mantém atualizados.

```
[Releaser de outro servidor] --HTTPS, chave do projeto--> [Caddy :443] --> [Silo :PORT] --> /data/silo (disco de dados)
[administrador] --navegador, chave raiz--> [Caddy :443] --> [console do Silo :PORT_CONSOLE]
```

> **Atenção!** O S3 de _backup_ tem de ficar numa **máquina diferente** das que geram os _backups_ (regra 3-2-1). Se possível, num _datastore_ separado também: um _backup_ no mesmo disco das aplicações se perde junto com elas.

## Máquina {#machine}

O que foi usado no **Embrapa I/O S3**, como referência:

| Recurso | Valor |
| --- | --- |
| CPU e memória | 4 vCPU e 16 GB de RAM (o Silo usa pouco; 2 vCPU e 4 GB bastam para poucos servidores) |
| Sistema | Ubuntu Server LTS, com Docker do repositório oficial |
| Disco do sistema | 100 GB (sistema, imagens e os _backups_ de configuração) |
| Disco de dados | **disco virtual separado**, sem formatação, do tamanho do acervo (2 TiB no **Embrapa I/O S3**) |
| Rede | IP público, se houver **Releasers** fora da rede da Embrapa; portas 80 e 443 abertas para fora |
| DNS | dois nomes: um para a API (ex.: `s3.cnpxx.embrapa.br`) e outro para o console (ex.: `console.s3.cnpxx.embrapa.br`) |

Ao pedir a VM à equipe de infraestrutura, peça o disco de dados **sem formatação** e, se possível, em _datastore_ separado do disco do sistema.

### Preparo do disco de dados {#disk}

O disco de dados vira um volume LVM com sistema de arquivos **XFS**, montado em `/data`. O LVM permite crescer o volume depois sem parar nada, e o XFS lida bem com objetos grandes e com muitos arquivos. No exemplo, o disco novo é o `/dev/sdb`: confira com `lsblk` antes, e confirme que ele está vazio com `wipefs -n /dev/sdb` (sem saída = sem assinatura).

```bash
sudo pvcreate /dev/sdb
sudo vgcreate data-vg /dev/sdb
sudo lvcreate -l 100%FREE -n silo data-vg
sudo mkfs.xfs -L silo /dev/data-vg/silo

sudo mkdir -p /data
sudo cp -a /etc/fstab /etc/fstab.bak
echo "UUID=$(sudo blkid -s UUID -o value /dev/data-vg/silo) /data xfs defaults,noatime,nofail 0 2" | sudo tee -a /etc/fstab
sudo systemctl daemon-reload
sudo mount -a
df -h /data
```

- A montagem é pelo **UUID**, que não muda se a ordem dos discos mudar.
- O `nofail` evita que a VM pare no _boot_ se o disco faltar. Nesse caso o Silo também não sobe (o volume dele aponta para `/data/silo`, que não existe no disco do sistema), e nada é gravado no lugar errado.
- Faça um _reboot_ de teste antes de colocar dados: `/data` tem de voltar montado e o Silo, de pé.

Para crescer o disco depois, peça a expansão do disco virtual e rode:

```bash
sudo pvresize /dev/sdb
sudo lvextend -r -l +100%FREE data-vg/silo   # o -r estende também o XFS
```

> **Atenção!** O XFS cresce, mas não diminui.

## Silo e Caddy pelo Releaser {#deploy}

1. Crie um projeto na plataforma (ex.: `cnpxx-s3`) com duas _apps_: uma do _boilerplate_ `silo` e outra do `caddy`.
2. Instale o **Releaser** na VM (veja [Releaser]({{ site.baseurl }}/docs/releaser)) e configure as duas _builds_ com `io install`.
3. Antes do primeiro _deploy_, crie o volume de dados do Silo **apontando para o disco de dados**. O nome segue a regra `{projeto}_{app}_{estágio}_data`:

```bash
sudo mkdir -p /data/silo
sudo docker volume create --driver local --opt type=none --opt o=bind --opt device=/data/silo cnpxx-s3_silo_release_data
```

4. Faça o _deploy_ (`io deploy --all`).

Se o Silo já tinha subido com um volume comum, no disco do sistema, a troca é:

1. `io stop <build> --down`;
2. `rsync -aHAX` do diretório do volume antigo para `/data/silo`;
3. `docker volume rm` do volume antigo e `docker volume create` com o _bind_, como acima;
4. `io restart <build>`, que recria os contêineres desde a versão `1.26.10-15` (antes dela, use `io deploy <build> --force`).

### Configuração do Silo {#silo}

As variáveis da _build_ do Silo usadas no **Embrapa I/O S3**:

| Variável | Valor | Por quê |
| --- | --- | --- |
| `BUCKET` | `backup` | um _bucket_ para todos os projetos; cada um grava em `<projeto>/<app>/<estágio>/` |
| `OBJECT_LOCK_DAYS` | `14` | cada arquivo enviado fica **imutável por 14 dias** (modo GOVERNANCE): nem um servidor invadido, nem um engano, consegue apagá-lo nesse prazo |
| `NONCURRENT_DAYS` | `30` | versões antigas (arquivos apagados ou substituídos) somem sozinhas em 30 dias, depois da retenção |
| `APP_ACCESS_KEY` | `backup` | usuário de aplicação criado pelo `init`, com acesso ao _bucket_ inteiro; para os projetos, use chaves próprias (abaixo) |
| `ROOT_USER` e `ROOT_PASSWORD` | gerados | administração; só para o console |

Com o Object Lock, **o espaço ocupado é maior que o acervo**: um arquivo apagado pela rotação do **Releaser** continua no disco até completar a retenção e a expiração. Dimensione o disco com folga.

Senhas e chaves só com letras e números (`[A-Za-z0-9]`), de 32 caracteres ou mais: alguns clientes S3 e _shells_ tratam mal os símbolos.

### Configuração do Caddy {#caddy}

Na _build_ do Caddy:

| Variável | Exemplo |
| --- | --- |
| `APP_DOMAIN` | `s3.cnpxx.embrapa.br` |
| `APP_PORT` | a `PORT` do Silo (API) |
| `CONSOLE_DOMAIN` | `console.s3.cnpxx.embrapa.br` |
| `CONSOLE_PORT` | a `PORT_CONSOLE` do Silo |
| `ACME_EMAIL` | e-mail para os avisos do Let's Encrypt |

O certificado é emitido sozinho no primeiro acesso, desde que os dois nomes apontem para a VM e as portas 80 e 443 estejam abertas. As portas do Silo não precisam ficar abertas para fora: só o Caddy as acessa.

> **Atenção!** O console dá **acesso total** com a chave raiz. Se não precisar dele fora da rede da Embrapa, deixe o nome do console só no DNS interno, ou acesse-o por túnel SSH.

## Uma chave por projeto {#keys}

Não distribua a chave `backup` (nem a raiz). Crie **uma chave por projeto**, com o nome _unix_ do projeto. Os dois caminhos gravam no mesmo lugar, `<bucket>/<projeto>/<app>/<estágio>/<arquivo>`, então a mesma política e a mesma chave servem tanto ao Backup S3 dos _clusters_ compartilhados quanto ao `io cloud` de um servidor com **Releaser**, e um projeto com estágios nos dois lugares fica com todos os _backups_ na mesma pasta. Se a chave de um projeto vazar, ela não lê nem apaga os _backups_ dos outros (e o Object Lock protege os dela própria por 14 dias).

A política abaixo deixa a chave **listar** o _bucket_ (o teste de acesso lista a raiz) e **ler, gravar e apagar** só dentro da pasta do projeto.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetBucketLocation", "s3:ListBucket", "s3:ListBucketVersions", "s3:ListBucketMultipartUploads"],
      "Resource": ["arn:aws:s3:::backup"]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetObjectVersion", "s3:PutObject", "s3:DeleteObject", "s3:DeleteObjectVersion", "s3:AbortMultipartUpload", "s3:ListMultipartUploadParts"],
      "Resource": ["arn:aws:s3:::backup/meu-projeto/*"]
    }
  ]
}
```

> **Atenção!** Troque `meu-projeto` na linha `"Resource": ["arn:aws:s3:::backup/meu-projeto/*"]` pelo **nome _unix_ do seu projeto**, o que aparece abaixo do nome no _card_ da _dashboard_ (ex.: `arn:aws:s3:::backup/pasto-inteligente/*`). É essa linha que restringe a chave à pasta do projeto: sem a troca, a chave não grava nada e o teste de acesso falha. Se o `bucket` não se chamar `backup`, troque também o nome dele nas duas linhas `Resource`.

A política **não** inclui `s3:BypassGovernanceRetention`, `s3:PutObjectRetention` nem nada de administração: a chave não consegue encurtar a retenção nem mexer no _bucket_. Listar o _bucket_ inteiro mostra os nomes dos arquivos dos outros projetos, mas não o conteúdo.

Um servidor com **Releaser** tem um só par de chaves no `.env`. Se ele hospeda _builds_ de mais de um projeto (o `io deploy` sem parâmetros, no próprio servidor, lista as _builds_ dele), use a chave de um dos projetos e acrescente à política dela uma linha `Resource` para cada projeto do servidor (ex.: `"arn:aws:s3:::backup/pasto-inteligente/*", "arn:aws:s3:::backup/calda-certa/*"`).

### Pelo console {#keys-console}

Os exemplos abaixo usam o projeto `pasto-inteligente`.

1. Entre no console (`https://console.s3.cnpxx.embrapa.br`) com o usuário raiz (`ROOT_USER` e `ROOT_PASSWORD` da _build_ do Silo).

   ![Tela de login do console do Silo]({{ site.baseurl }}/assets/img/s3/13.png){: width="90%" .img-center }

2. **Policies → Create Policy**: em **Policy Name**, o nome _unix_ do projeto; em **Write Policy**, cole a política acima, **já com `meu-projeto` trocado** na linha `Resource`. Salve com **Save**.

   ![Create Policy com o nome do projeto e a política, com a pasta do projeto na linha Resource]({{ site.baseurl }}/assets/img/s3/14.png){: width="90%" .img-center }

   A política aparece na lista **IAM Policies**:

   ![Lista IAM Policies com a política do projeto]({{ site.baseurl }}/assets/img/s3/15.png){: width="90%" .img-center }

3. Gere a senha, só com letras e números:
   ```bash
   openssl rand -base64 48 | tr -dc A-Za-z0-9 | head -c 40
   ```
4. **Identity → Users → Create User**: em **User Name**, o nome _unix_ do projeto (é a _access key_); em **Password**, a senha gerada (é a _secret key_). Em **Assign Policies**, digite o nome do projeto e marque **somente** a política criada no passo 2. Salve com **Save**.

   ![Create User com o nome do projeto, a senha e só a política do projeto marcada]({{ site.baseurl }}/assets/img/s3/16.png){: width="90%" .img-center }

   O usuário aparece na lista **Users**:

   ![Lista Users com o usuário do projeto]({{ site.baseurl }}/assets/img/s3/17.png){: width="90%" .img-center }

Essa chave (o nome do projeto e a senha) é a que vai no Backup S3 do **Dashboard** ([abaixo](#clusters-setup)) e no `io cloud --setup` do **Releaser** ([abaixo](#releaser)). Guarde a senha num cofre: o console não a mostra de novo.

### Pela linha de comando {#keys-cli}

O _boilerplate_ traz o `mc` no serviço `mc` (perfil `cli`). No diretório da _build_ do Silo, com a política salva em `policy.json` (já com o nome do projeto na linha `Resource`):

```bash
env $(cat .env.io) docker compose run --rm -T mc admin policy create silo meu-projeto /dev/stdin < policy.json
env $(cat .env.io) docker compose run --rm mc admin user add silo meu-projeto <SENHA>
env $(cat .env.io) docker compose run --rm mc admin policy attach silo meu-projeto --user meu-projeto
```

Os usuários e políticas entram no _backup_ de configuração do Silo (abaixo).

## Configuração em cada servidor {#releaser}

No servidor que vai enviar os _backups_, com o **Releaser** `1.26.10-15` ou mais novo (`io upgrade`):

```bash
io cloud --setup
```

| Pergunta | Resposta |
| --- | --- |
| _Endpoint_ | `https://s3.cnpxx.embrapa.br` |
| _Bucket_ | `backup` |
| _Access key_ e _secret key_ | a chave do projeto ([acima](#keys)) |
| Região | `auto` (o padrão; o Silo aceita) |

O assistente testa a **listagem** e a **gravação** antes de salvar. O teste de gravação abre e cancela um _upload multipart_ no diretório de uma _build_ do servidor, sem deixar nada no _bucket_: um arquivo de teste comum ficaria retido pelo Object Lock por 14 dias. Depois:

```bash
io cloud <projeto>/<app>@<estágio>             # primeira cópia, manual
io cloud <projeto>/<app>@<estágio> --verify    # compara os arquivos dos dois lados pelo hash
io cloud <projeto>/<app>@<estágio> --list      # o que está no bucket e o que a rotação faria
```

Por fim, ligue `"auto": { "cloud": true }` no arquivo da _build_ para a cópia diária. O `io check`, e o `check` diário por e-mail, voltam a testar listagem e gravação todo dia.

> **Atenção!** A primeira cópia envia **todo** o acervo de _backups_ da _build_ e pode levar horas. Acompanhe o espaço livre em `/data` do S3 enquanto ela roda.

Para restaurar no servidor um arquivo do _bucket_ (inclusive os da pasta `upload/`, para migrações), use o `io restore` do **Releaser** `1.26.10-16` ou mais novo, com as mesmas etapas do [_restore_ dos _clusters_](#clusters-restore): _backup_ prévio protegido por 30 dias, _download_, conferência e o serviço `restore` da _app_. Detalhes na [documentação do Releaser]({{ site.baseurl }}/docs/releaser#restore).

## Backup S3 dos clusters compartilhados {#clusters}

Nas _builds_ hospedadas nos _clusters_ compartilhados da plataforma, a cópia para o S3 é configurada por um [_Architect_]({{ site.baseurl }}/docs/squads#architect) (arquiteto da solução) do projeto no **Dashboard**: no menu do _card_ do projeto, item **Backup S3** da seção **Avançado**. O _bucket_ é do próprio projeto, em geral o S3 da Unidade, com uma chave restrita ao projeto ([acima](#keys)). As _builds_ com **Releaser** ficam de fora: nelas, a cópia é o `io cloud`.

![Item Backup S3 no menu do card do projeto]({{ site.baseurl }}/assets/img/s3/01.png){: width="45%" .img-center }

### Configuração {#clusters-setup}

O assistente tem dois passos:

1. **_Bucket_**: _endpoint_ (`https://`), _bucket_, região (`auto` serve para o Silo) e a chave do projeto. O botão **Testar o Bucket** lista o diretório do projeto e abre e cancela um _upload multipart_, sem deixar nada no _bucket_. A configuração só é salva se o teste passar. O segredo é guardado cifrado e nunca mais é exibido, só os últimos caracteres.

   ![Passo Bucket, com o teste de listagem e gravação aprovado]({{ site.baseurl }}/assets/img/s3/02.png){: width="80%" .img-center }

2. **Agenda e Retenção**: os estágios incluídos (alpha, beta, release), a hora da rodada diária (horário de Brasília; cada _build_ é deslocada dentro dessa hora) e a retenção no formato do **Releaser**, `D/S/M/A` (padrão `7/4/3/1`, com pelo menos um diário ou um semanal).

   ![Passo Agenda e Retenção: estágios, horário e retenção 7/4/3/1]({{ site.baseurl }}/assets/img/s3/03.png){: width="80%" .img-center }

Na rodada diária, para cada _build_ incluída, a plataforma roda o serviço `backup` da _app_, envia o arquivo para `<projeto>/<app>/<estágio>/`, confere o tamanho no _bucket_, **apaga o arquivo do _storage_ do _cluster_** e aplica a retenção. A cada 15 minutos, os _backups_ gerados fora da rodada (pelo botão **Backup** do _Health Check_ e antes de cada _deploy_) também sobem. Falhas chegam por e-mail aos _Architects_ do projeto.

A tela tem três abas:

- **Configuração**, com o resumo do _bucket_, da chave, da agenda e da retenção, o último teste e o último envio, e os botões **Executar Agora** (a rodada fora do horário, no máximo uma a cada 10 minutos), **Reconfigurar**, **Testar o Bucket** e **Desligar**;

  ![Aba Configuração do Backup S3 ativo]({{ site.baseurl }}/assets/img/s3/04.png){: width="80%" .img-center }

- **_Builds_**, com a situação de cada uma: incluída, estágio desligado, desativada, **Releaser**, ou sem serviço `backup`. É comum as _apps_ de _front-end_ não terem esse serviço: elas ficam de fora sem gerar erro;

  ![Aba Builds, com a situação de cada build]({{ site.baseurl }}/assets/img/s3/05.png){: width="80%" .img-center }

- **Histórico**, com cada envio e cada limpeza da retenção, a origem, o tamanho e o SHA-256 do arquivo, com filtros por _app_ e estágio.

  ![Aba Histórico, com envios agendados e limpezas da retenção]({{ site.baseurl }}/assets/img/s3/06.png){: width="80%" .img-center }

### Restore {#clusters-restore}

No _Health Check_ da _build_, o item **Restaurar Backup** do menu lista os arquivos do _bucket_ da _app_: os dos três estágios e os da pasta `upload/`.

![Item Restaurar Backup no menu do Health Check]({{ site.baseurl }}/assets/img/s3/07.png){: width="60%" .img-center }

![Lista de arquivos do bucket da app, dos três estágios e da pasta upload]({{ site.baseurl }}/assets/img/s3/08.png){: width="80%" .img-center }

O _restore_ é exclusivo dos _Architects_ do projeto. Escolhido o arquivo, a plataforma envia um PIN ao e-mail de quem pediu, válido por 5 minutos. Confirmado o PIN, o pedido entra numa **fila única** (um _restore_ por vez em toda a plataforma), com o andamento na própria tela e o resultado por e-mail.

![Confirmação do restore pelo PIN de 6 dígitos enviado por e-mail]({{ site.baseurl }}/assets/img/s3/09.png){: width="80%" .img-center }

As etapas são:

1. **Pré-restore**: um _backup_ da _build_ atual, enviado ao _bucket_ para permitir voltar atrás. Ele fica protegido da retenção por 30 dias.
2. **Download** para o _storage_ do _cluster_, que precisa ter **o dobro do tamanho do arquivo** livre.
3. **Conferência**: SHA-256 (o do histórico ou o informado), integridade do `gzip` e leitura do `tar`.
4. **_Restore_**: o serviço `restore` da _app_, com o arquivo em `BACKUP_FILE_TO_RESTORE`.

![Andamento do restore na etapa de conferência]({{ site.baseurl }}/assets/img/s3/10.png){: width="80%" .img-center }

Ao fim, a tela mostra o resultado do último _restore_ e o _backup_ prévio aparece na lista com a origem **Pré-restore**, pronto para desfazer a operação, se preciso.

![Restore concluído e o backup prévio na lista, com a origem Pré-restore]({{ site.baseurl }}/assets/img/s3/11.png){: width="80%" .img-center }

Restaurar o arquivo de outro estágio (ex.: o release no alpha) é permitido, com confirmação explícita. Enquanto o _restore_ está na fila ou rodando, a _build_ não aceita _backup_, _restart_, _undeploy_ nem remoção.

### Migrar dados para uma build {#clusters-upload}

Para levar dados de fora da plataforma (de um servidor antigo, de outro sistema), envie o arquivo ao _bucket_ em `<projeto>/<app>/upload/` com qualquer cliente S3 (o console do Silo, o `mc`, o `rclone`), usando a chave do projeto. Ele aparece no **Restaurar Backup** com a origem **Uploaded**, e o _restore_ pede uma confirmação a mais, porque a plataforma não tem o SHA-256 dele (pode ser informado no campo opcional).

![Arquivo enviado à pasta upload, com o SHA-256 opcional e as confirmações]({{ site.baseurl }}/assets/img/s3/12.png){: width="80%" .img-center }

- O nome tem de terminar em `.tar.gz` e ter só letras, números, ponto, hífen e sublinhado. Uma data no nome (`AAAA-MM-DD_HH-MM-SS`, em UTC) é usada como data do _backup_; sem ela, vale a data do envio.
- O conteúdo tem de ter **a mesma estrutura do arquivo que o serviço `backup` da _app_ gera**, porque é o serviço `restore` da _app_ que o lê. O caminho mais seguro é gerar um _backup_ da _build_ no destino, ver a estrutura dele (`tar -tzf`) e montar o arquivo de migração igual. Quando o `README.md` da _app_ (ou do _boilerplate_) descreve o formato, siga-o.
- Num _bucket_ com Object Lock, como o do Silo acima, a regra vale também para a pasta `upload/`: o arquivo enviado não pode ser apagado por 14 dias.

## Monitoramento {#monitoring}

- **Saúde:** `https://s3.cnpxx.embrapa.br/minio/health/live` responde 200 com o Silo de pé. É o que o **Embrapa I/O** monitora no Gatus.
- **Disco:** alerte o uso de `/data` acima de 80% (aviso) e de 90% (crítico), e também a **falta** da métrica, que indica `/data` desmontado ou coletor parado. No **Embrapa I/O**, as métricas vão pelo Alloy para o Prometheus da plataforma, e os alertas são regras do Grafana.
- **Conteúdo do bucket:** `mc du --depth 3 silo/backup/` mostra o espaço por projeto; `mc ls --recursive --incomplete silo/backup/` lista _uploads_ inacabados.

## Backup e recuperação do próprio S3 {#recovery}

O serviço `backup` do _boilerplate_ `silo`, que o **Releaser** roda todo dia, guarda **só a configuração**: usuários, políticas e _buckets_ com versionamento, Object Lock e expiração. Não copia os objetos: os _backups_ das aplicações são, eles mesmos, a cópia; a original continua em cada servidor. Se o S3 for perdido, suba um Silo novo, restaure a configuração (serviço `restore`) e os servidores voltam a enviar tudo na próxima execução do `io cloud`.

O arquivo de _backup_ da configuração contém as chaves dos usuários: trate-o como segredo.
